# faakt.io illustrations

This repository-local workflow works with any AI agent with image-generation access. Read this file directly; no Codex installation or proprietary skill loader is required. Run commands from the repository root with Node.js 18 or newer.

Create recognizable, restrained editorial raster artwork from each post's `illustration` metadata. Optimize for small mobile cards and one successful generation per post.

## Scope and inputs

- Locate the faakt.io checkout and read applicable CLAUDE.md/AGENTS.md instructions. Preserve existing work. Do not alter production rendering or migrate the dataset unless requested.
- Extract only requested IDs with the bundled helper; never load all of posts.json into model context. Omitted IDs are an error, not permission to generate the full dataset.
  `node skills/faakt-illustrations/scripts/prepare.mjs --root . --ids '018,006'`
- The helper prints compact prompts only for missing assets and reports cached IDs. It makes no AI calls and writes no files.
- When the user explicitly requests regeneration of a visually defective cached asset, add `--force` for only those IDs: `node skills/faakt-illustrations/scripts/prepare.mjs --root . --ids '003' --force`. Never use `--force` for an unreviewed batch.
- Read the title and full content of each requested post before generation, even when metadata is complete. Use concept, primary_subject, secondary_subjects, visual_keywords, composition_hints, scene_type, mood and palette as the visual source, checked against the central claim of the text. Do not substitute a category/title template.

### Choose a simple motif according to context

- Read the full post and choose according to context: either a recognizable subject or an immediately readable relationship, contrast or interaction. A scientific point can be the image itself when its representation stays simple. If it requires many separate objects, multiple steps or arrows tracing which component implies the next, select one recognizable aspect instead. The text can supply the explanation; the image need not prove or summarize it.
- A relevant standalone object is sufficient, including for science. A moving ambulance can accompany Doppler effect; a book with a prohibition sign can accompany a banned novel; a pulsar with a simple beam can accompany periodic radio pulses. Do not combine the pulsar, Earth, waveform, magnetic field and observing equipment merely because all relate to the text. These examples guide simplification, not mandatory templates.
- Prefer one strong motif. Add supporting symbols or objects only when they improve immediate recognition of that selected aspect. Relevance alone is not a reason to draw everything. An isolated particle, instrument or portrait may accompany its actual topic without demonstrating the discovery.
- Treat metadata as context, not a required inventory. If it describes an entire experiment or sequence, simplify its visual concept before generation; align scene_type and composition_hints with that selection. Do not blindly truncate lists or discard facts arbitrarily. Retain original metadata in provenance when using a deliberately simplified prompt.
- A simple diagram, paired contrast or interaction is appropriate when understood at a glance. Objects, portraits and single actions are equally valid. A single helpful arrow is not a defect; a chain of arrows needed to decode many components is a reason to simplify to one recognizable aspect. Remove apparatus, observers, traces and steps added merely for completeness.
- Preserve the selected subject's identity and avoid visible contradictions. A historical hypothesis may be depicted as the idea being discussed, without claiming it is true. Leave dates, national context and qualifications to the article unless they help recognition of the chosen motif.
- Default to no text. Do not add the pictured object's name as a caption. A familiar prohibition sign or other concise supporting symbol is welcome; explanatory labels are not a substitute for a readable silhouette.
- Preserve unrelated accepted assets and explicit user selections: 028's meditating Buddha with empty hands, 044's planet near its star, and first versions 188, 200 and 212. General simplification does not authorize regenerating them.

## Reusing artwork across duplicate posts

- Editorial duplication and visual compatibility are separate decisions. Two posts can teach the same principle through different experiments, events or people. Before reusing an asset, read every destination's full text, inspect both its current image and the proposed source, and compare the concrete scene, actors, props and causal relationship. A matching topic, valid alpha or lower generation cost does not establish a semantic fit.
- Preserve the best content-matching composition when fixing a background. Prefer a transparent edit/regeneration of that image over replacing it with a different story that merely shares the topic. When the user points to a previous version, inspect it from the workspace or version history and use it as a reference; this is an explicit exception to the default of not attaching previous images.
- Check the direction of the effect, not just the objects. For post 009, the peg-turning task and unequal payments matter, but the small-payment participant must show the more positive appraisal. Showing the larger payment producing more enthusiasm reverses the finding.
- Example: 009's boring-task experiment and 082's failed prophecy both concern cognitive dissonance, but a religious group is not a replacement scene for 009. Do not automatically share either concrete story across both. If the user explicitly chooses one shared illustration (as with the corrected 009 used for both), record that it illustrates the principle through 009's experiment and only accompanies 082's different account; do not claim it depicts both narratives or change either article to fit the image.
- In provenance, distinguish topic-level accompaniment from an exact scene match, and record the source ID, actual submitted prompt, image hash and compatibility rationale. Background acceptance must never silently become semantic acceptance.

## Generation and token budget

- Use an image-generation model available in the current agent environment and follow its tool instructions. Prefer an existing image tool over adding a service. Tool names and parameters depend on the agent; no particular vendor or SDK is required. One call per missing post, one complete image, no contact sheets, variants or procedural SVG substitutes. No separate language-model call is needed to rewrite prompts.
- Check existing assets and provenance first. Reuse static/illustrations-ai/<id>.webp or <id>.png; check any project manifest for another registered path. Never regenerate just because the shared prompt changed. Flag stale metadata for review; regenerate only when requested.
- A reported visible background rectangle, missing alpha channel or mismatched card color is a substantive defect and authorizes one targeted `--force` regeneration when the user asks to fix it.
- Send the shared style plus that post's compact metadata only. Do not attach the dataset, screenshots, previous images or conversation history as visual references by default. Keep the meaningful concept; remove redundant keyword repeats in preparation.
- Prefer a genuinely transparent image background. When the image tool exposes a transparency/background parameter, set it explicitly; prompt wording alone does not guarantee an alpha channel. Do not flatten transparent output during conversion.
- For tiny card artwork, prefer the smallest supported landscape generation size and low quality when the selected tool exposes these controls. Set these parameters explicitly when supported; never request high/auto quality or oversized output just for polish. When parameters are unavailable, record that generation cost cannot be capped and use the flat thumbnail prompt; do not invent unsupported arguments or claim that wording enforces lower computation. Built-in tools may choose their own dimensions/quality.
- Do not switch to paid APIs, install an image service or use an API key without user authorization. If no authorized image-generation model is available, report the blocker instead of creating procedural substitutes. Before an explicitly authorized API fallback, verify current size/quality constraints and pricing for the selected model.
- Generated pixel size/quality and retries affect image-generation usage. Short prompts reduce text input only. Resizing or WebP conversion afterwards saves transfer/storage, not generation tokens. A shared style string is not a guarantee of provider-side prompt caching.
- Never print base64 data or the entire generation response into text/context. Retain the result internally and print only its saved path or small metadata. Inspect saved files with an image viewer.

## Visual specification

- At thumbnail size, recognize the selected subject immediately. Judge it together with the title and article. It need not explain the full post on its own. Supporting symbols are optional, not a reason to accumulate a second explanation.

The helper contains the single shared STYLE; use it verbatim rather than adding ?detailed?, ?cinematic?, ?high quality?, ?beautiful landscape? or similar embellishments. Target visual simplicity during generation, before resizing.

- Design for **160×90 CSS pixels**; it must also look clean at 320×180. Deliver at 640×360 for density, not additional detail.
- Center the visible main motif optically within the full image, with balanced empty margins. Do not reserve an empty text column. Use asymmetry only when it helps the particular meaning, interaction or direction of action, and record why. Check the actual alpha-visible artwork, not just the canvas dimensions. During final sizing, trim surplus fully transparent outer padding and center the complete visible motif on a transparent canvas unless that would remove intentional contextual spacing; never crop visible parts or force mirrored symmetry.
- Aim for **5–8 large flat shapes**, **no more than 3 foreground colors**, and **at least one third transparent negative space**. These are art-direction targets, not claims of machine-enforced counts. Avoid adding scientific features merely to make an accompanying image exhaustive.
- Use one main subject. Include supporting symbols and secondary subjects when they meaningfully relate to the content and preserve a clear composition. Prefer flat shapes with at most one shadow plane; avoid realistic lighting, reflections, grain, fine linework and dense repeating elements. Restrained translucent shapes or soft transitions are allowed when mist, light or another soft medium is itself the meaningful subject. This does not authorize a decorative glow or an opaque background rectangle.
- Prefer one striking main motif, even when that leaves much of the article unillustrated. Simplicity comes from choosing less content before generation. Post 040 is an existing complex composition, not a target for new work. Remove even relevant panels or objects when the selected motif is already sufficient.
- Environment: reduce to 2–3 broad planes. For a river, use a broad winding ribbon and simple banks; do not invent a sunset, mountains, forest, rocks, waves or sparkling water. Include such objects when they meaningfully relate to the content and keep the composition easy to understand.
- Portrait: use a face/robe silhouette with a few identifying features, not individual hair strands, wrinkles or embroidered cloth. Objects: prioritize outer contour and the minimum identifying internal marks.
- Preserve the factual identity of the selected subject; metadata is not a checklist. Generic finish cues (`material_texture`, `architectural_detail`, ?detailed depiction?) do not authorize extra scenery or texture. The helper omits those two generic keywords from the prompt, while keeping original metadata unchanged and hashed. Architecture essential to the concept/primary subject must still be shown simply.
- Inspect the current card CSS before generation. The current `.card-face` surface is a vertical gradient from `#141414` to `#0d0d0d`, so transparent output is preferred and matches the card everywhere. Never use approximate blacks such as `#000`, `#111` or a model-invented near-black.

### Background contract

- A black, near-black or dark gradient is forbidden as image background in every mode. The card already owns its background; the asset must never imitate that gradient because any positional or compression difference creates a visible rectangle.
- Preferred output: PNG or WebP with a real alpha channel. Empty areas must have alpha 0, including corners; there must be no baked-in black rectangle, halo, vignette or colored fringe.
- If the selected tool cannot generate transparency, read the actual background at the illustration's placement from `src/lib/components/PostCard.svelte`. Use that exact CSS color as one uniform solid fill in both the prompt and any letterbox/padding operation. Every empty corner and edge pixel must use the identical value. For the current lower card area the fallback is `#0d0d0d`; re-check it whenever card styling changes.
- A flat opaque fallback cannot perfectly match a gradient across the whole image. Do not claim a seamless match; prefer transparency or report this limitation.
- When converting with Pillow, preserve `RGBA` and save alpha-capable WebP/PNG. Do not call `.convert('RGB')` and do not pad with an arbitrary black. Check corner alpha values or compare the asset on the real card before accepting it.
- Reject an opaque asset when empty background pixels vary across corners or edges; that variation indicates a gradient, vignette, glow or compression-contaminated backdrop. Regenerate it as transparent rather than trying to color-correct the gradient.

### Acceptance at thumbnail scale

Judge the illustration together with the card title and article. It should offer an immediately recognizable motif, not replace every detail of the text. Before spending a correction, identify a concrete visible contradiction or loss of the central idea; a possible literal interpretation of an editorial symbol is not sufficient. Keep relevant factual distinctions, but verify a suspected mismatch at a larger view before declaring an error from overlapping silhouettes. Small counting ambiguities warrant replacement only when they materially change the depicted contrast. Clear reversals of an effect, wrong subjects and unreadable compositions remain substantive defects.

Do not add country names, flags or explanatory labels merely because the prose supplies context absent from the image. A human scene of reporting or censorship may accompany the actual article better than a fully labelled diagram. Likewise, a symbolic connection can make entanglement recognizable without asserting communication faster than light. Assess what the whole image communicates rather than rejecting a particular mark in isolation.

When a correction is justified, preserve the original, make the smallest relevant change and compare both versions at the same card size. Deliver the replacement only if it improves the identified problem while retaining the original's action, expressiveness and readability. For a user-requested simplification, a clearer selected motif with fewer explanatory elements is the intended improvement; it need not retain the entire previous diagram. If the supposed defect remains uncertain, retain the original and record the limitation; do not launch a refinement loop.

User-selected compositions `188`, `200` and `212` use their first generated versions: the acted-out trolley comparison, the newspaper seller contrasted with muted wartime reporting, and paired measurement outcomes linked by symbolic curves. Preserve these choices. The curves in `212` accompany a shared quantum state; they are not a literal signal path. These decisions illustrate the review criteria above, not universal requirements for future pictures.

Check the chosen aspect, readability and factual compatibility with the article. Do not reject a relevant standalone object because it omits the experiment, causal chain, context already in the text or a self-contained explanation. Record whether it accompanies the topic or illustrates a particular relationship; neither role is inherently better. Review supporting objects for usefulness to the selected motif, not simply for relevance to the whole article.

View the result at 160×90 and 320×180, not only the full-size output. The primary subject should be immediately identifiable. Reject as over-detailed if it relies on realistic light, fine textures, repeated tiny shapes or scenery unrelated to the concept. Do not call a downscaled painting a successful minimalist illustration. Record any failure honestly; no automatic regeneration loop. For an explicit repair request, make one targeted replacement or edit and inspect it before acceptance. If it still has a substantive semantic defect, allow one additional edit that simplifies the motif within the user's requested scope; do not generate cosmetic variants or accept the defect merely to meet a retry count. Stop and report any failure remaining after that bounded correction. Do not try to force lower image-generation cost through prompt wording when the tool lacks size/quality controls.

## Static delivery and cache

- Copy every final image into the checkout. Image tools may save output in an agent-specific directory or return binary/base64 data. Save the resulting image inside the repository; never reference agent-specific external paths from the app.
- Prefer final 640×360 alpha-capable WebP (quality around 78–82) for a 320 CSS pixel-wide card at 2× density. Preserve aspect ratio and use transparent padding rather than cropping meaningful subjects. For other card proportions adapt dimensions. Use an existing image utility if available; keep a transparent PNG when WebP alpha conversion is unavailable.
- Use `python skills/faakt-illustrations/scripts/fit-image.py --input GENERATED.png --output static/illustrations-ai/ID.webp` for final sizing and balanced transparent margins. It centers the alpha≥16 footprint to ignore near-invisible distant specks while preserving all alpha-visible pixels. Add `--preserve-spacing` only for meaningful intentional asymmetry and `--replace` only for an authorized replacement. Check optical balance visually: alpha geometry cannot identify a semantic focal subject. The helper requires Pillow, does not generate images, and keeps the input original.
- Do not overwrite established asset paths/manifest entries unintentionally. For new assets use static/illustrations-ai/<id>.webp (or .png). Save the exact submitted prompt, metadata/prompt hash, generation method and final image path in a small manifest or sidecar. Merge entries; never replace the six-post prototype manifest wholesale. Do not record unreported model names, quality, token counts or costs as facts.
- Inspect at actual card scale once: correct subject, readable silhouette, no unwanted text, and no visible image rectangle or mismatched black around the edges. Do not regenerate for minor aesthetic preference without a review request; report issues. Stop repeated attempts on a substantive failure and report it.
- After a requested correction, verify both the replacement file and the card registration. A previously rejected asset may exist in the gallery while being excluded from cards; once its correction is accepted, restore its card ID and clear the stale rejection note. A saved image alone does not complete a request to fix a missing card illustration.
- For a requested rollback, restore the saved earlier asset without a new generation. Restore its actual submitted prompt and image hash in provenance, record the user's selection, and remove the superseded rejection rationale from the current review. A subsequently updated STYLE must not be presented as the restored image's original prompt.
- If preview is requested, reuse /dev/illustrations-ai and existing card/badge styling; honor the /faakt.io base path. Keep generated assets static with no runtime AI. Follow repository handoff-document requirements for gallery changes.
- If the user explicitly asks to display an existing image despite editorial review failures, keep it registered and record the actual caveats and user override instead of silently hiding it. This concerns local editorial checks, not an image provider refusing to produce a file.
- Stop at the requested images and local review. Report paths/preview, method, skipped cached IDs and blockers concisely. Creating this skill alone does not authorize new image generations.
